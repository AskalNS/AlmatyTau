# Архитектура — сайт ТОО «Almaty Tau Management»

Документ фиксирует технические решения по ТЗ «Работы по созданию (разработке) официального
веб-сайта ТОО «Almaty Tau Management», код ЕНС ТРУ 631112.000.000000.

Срок: 30 календарных дней. Гарантия: 12 месяцев.

---

## 1. Ключевое решение: модульный монолит, а не микросервисы

Сайт контентный: ~15 сущностей, чтение существенно преобладает над записью, нагрузка по ТЗ —
500 одновременных сессий (~50 rps). Дробление бэкенда на сетевые сервисы здесь даёт только
издержки: распределённые транзакции, 8 контейнеров на сопровождении в течение 12 месяцев
гарантии и невозможность уложиться в 30 дней.

Задача «правка в одном месте не должна ломать другое» решается **границами модулей внутри
одного процесса**, а не сетевыми границами.

### Правила модульности (обязательны к соблюдению)

1. Модуль — это папка в `src/modules/<name>/` со своим контроллером, сервисом, DTO, Prisma-запросами и тестами.
2. Модуль **не импортирует внутренности другого модуля**. Только публичный экспорт: `<Name>Module` и `<Name>Service`.
3. Кросс-модульные обращения — через DI NestJS, никогда через прямой импорт файлов.
4. Общие вещи (Prisma-клиент, guards, pipes, утилиты) живут в `src/common/` и `src/infra/`.
5. Каждый модуль имеет e2e-тест на свои роуты. Правка в чужом модуле, ломающая контракт, падает на CI.

Если через год какой-то модуль реально вырастет — он выносится в отдельный сервис за день,
потому что границы уже проведены.

## 2. Состав репозиториев (3 отдельных проекта)

```
atm-backend/          NestJS + Prisma + PostgreSQL — REST API, единственный владелец БД
atm-web/              Next.js 15 (App Router, SSR/ISR) — публичный сайт
atm-admin/            React 19 + Vite (SPA) — административная панель
packages/contracts/   Общие TypeScript-типы и Zod-схемы API (подключаются во все три проекта)
```

Правила связи:

- `atm-web` и `atm-admin` **никогда не обращаются к БД напрямую** — только HTTP к `atm-backend`.
- Весь контент сайта читается из PostgreSQL. Захардкоженных текстов в вёрстке нет,
  кроме служебных подписей интерфейса (они в i18n-файлах фронта).
- `packages/contracts` — единственный источник правды по формату API. Изменил ответ эндпоинта —
  сборка фронтов падает сразу, а не в проде.

Развёртывание: три образа + Postgres + Redis + MinIO в одном `docker-compose.yml`. Заказчику
передаётся целиком (п. XIII, XV ТЗ — никакого вендор-лока).

## 4. Мультиязычность (kk / ru / en)

ТЗ требует **отдельную структуру контента и независимое редактирование** для каждого языка.
Решение: таблица переводов на каждую переводимую сущность.

```prisma
model News {
  id          String            @id @default(cuid())
  slug        String            @unique
  coverId     String?
  publishedAt DateTime?
  status      PublishStatus     // DRAFT | PUBLISHED | ARCHIVED
  translations NewsTranslation[]
}

model NewsTranslation {
  id       String  @id @default(cuid())
  newsId   String
  locale   Locale  // KK | RU | EN
  title    String
  excerpt  String?
  body     Json    // блочный контент
  seoTitle String?
  seoDesc  String?

  news     News    @relation(fields: [newsId], references: [id], onDelete: Cascade)
  @@unique([newsId, locale])
}
```

- Публичный API отдаёт запрошенную локаль; если перевода нет — сущность **не показывается**
  на этом языке (а не подменяется русским). Это и есть «независимое редактирование».
- URL: `/kk/news/...`, `/ru/news/...`, `/en/news/...` — отдельный URL на язык, как требует п. IV.
- `hreflang`, отдельные `sitemap-kk.xml` / `-ru` / `-en`, свои Title/Description на язык (п. III, IX).
- В админке — переключатель языка внутри карточки сущности и индикатор «переведено / нет».

Важно: контент в БД — в UTF-8, казахские специфичные символы (ә, ғ, қ, ң, ө, ұ, ү, һ, і)
проверяются в тестах, коллация БД `C.UTF-8`.

## 5. Блочный контент

Разделы «О компании», «Проект АГК», «Медиацентр» требуют текст, фото, инфографику, схемы,
видео, презентации, интерактивные карты. Хардкодить вёрстку под каждый раздел нельзя —
ТЗ прямо разрешает Заказчику менять структуру на любом этапе (п. IV).

Поэтому тело страницы хранится как массив типизированных блоков в `Json`:

```
text | heading | image | gallery | video | file | quote | stats | map | accordion | embed
```

Валидация блоков — Zod-схема из `packages/contracts`, общая для бэка, админки и фронта.
Рендер — реестр React-компонентов по типу блока. Новый блок = новый компонент + схема,
существующие страницы не затрагиваются.

## 6. Роли и права (п. V)

| Право | Администратор | Редактор |
|---|---|---|
| Контент (страницы, новости, медиа, документы, вакансии, ссылки) | ✔ | ✔ |
| Управление пользователями и правами | ✔ | ✘ |
| Настройки системы, конфигурация | ✔ | ✘ |
| Просмотр журнала аудита | ✔ | ✘ |

Реализация: `RolesGuard` NestJS + декоратор `@Roles(Role.ADMIN)` на уровне контроллера.
Админка скрывает недоступные разделы, но **решение о доступе принимает только бэкенд**.

## 7. Информационная безопасность (п. X)

| Требование ТЗ | Реализация |
|---|---|
| SSL, обязательный HTTPS | Nginx + Let's Encrypt, HSTS, редирект 80→443 |
| Ограничение доступа к админке | Отдельный поддомен `admin.`, опционально allow-list IP |
| Сложная парольная политика | Валидация при установке пароля, argon2id для хранения |
| 2FA | TOTP (`otplib`), обязательна для роли Администратор |
| Brute Force | `@nestjs/throttler` + блокировка учётной записи после N попыток |
| SQL-инъекции | Prisma — параметризованные запросы, сырого SQL нет |
| XSS | Санитизация HTML на входе (`sanitize-html`), CSP-заголовки, React экранирует по умолчанию |
| CSRF | JWT в заголовке Authorization (не в cookie), строгий CORS-allow-list |
| Загрузка вредоносного кода | Проверка MIME по содержимому, whitelist расширений, файлы отдаются с отдельного домена |
| Журналирование действий | Модуль `audit`: кто, что, когда, старое/новое значение, IP |
| Мониторинг подозрительной активности | Логи в Loki + алерты на всплеск 401/403 |

Персональные данные (форма обратной связи, вакансии) — согласие на обработку, срок хранения,
хостинг в РК. Закон РК «О персональных данных и их защите» (п. I ТЗ).

## 8. Производительность: Desktop ≥ 90 / Mobile ≥ 80 (п. VIII)

Это самое рискованное требование ТЗ. Меры:

- **SSR/ISR в Next.js** — HTML приходит готовым, а не собирается в браузере. SPA здесь физически не возьмёт 90.
- Главная страница требует видео/анимированный баннер (п. 1) — это главный враг LCP.
  Решение: постер-изображение как LCP-элемент, видео подгружается после `load`, `preload="none"`,
  на мобильных — статичное изображение вместо видео.
- Изображения: `sharp` → AVIF/WebP в нескольких размерах при загрузке, `next/image`, явные width/height (нет CLS).
- ISR: контентные страницы пререндерятся, ревалидация по вебхуку из админки при публикации.
- Redis-кэш ответов API, кэш-заголовки, Brotli в Nginx, CDN на статику.
- Шрифты: `font-display: swap`, самохостинг, только нужные начертания (кириллица + казахская латиница/кириллица).
- Минификация CSS/JS, code splitting — из коробки Next.js.
- Оптимизация запросов: индексы под каждый список, никаких N+1 (проверяется тестами на количество запросов).

Замер PageSpeed включён в чек-лист приёмки этапа 4, а не оставлен на финал.

## 9. Доступность и версия для слабовидящих (п. VI)

По ТЗ обязательна по закону. Не плагин-виджет, а режим в самом сайте:

- Переключатель: высокая контрастность, размер шрифта (3 ступени), отключение изображений.
- Настройка сохраняется в cookie и применяется на сервере — без мигания при загрузке.
- `alt` — обязательное поле при загрузке изображения в админке (нельзя сохранить без него).
- Семантическая разметка, навигация с клавиатуры, ARIA, контраст по WCAG 2.1 AA.

## 10. Интеграции

- **REST API** — публичный, документирован через Swagger (`/api/docs`). Это прямое требование
  п. II: интеграция с корпоративными системами Заказчика без переработки кода.
- **Карты** — 2GIS или Яндекс.Карты (в РК работают стабильнее Google). Абстрагированы за
  компонентом `<MapBlock>`, чтобы будущий «цифровой двойник АГК» (п. VI) подменил реализацию
  без правок остального кода.
- **Веб-аналитика** — Google Analytics 4, подключается через настройки, не хардкодом (п. IX).

## 11. Инфраструктура и передача Заказчику

```
Nginx (TLS, Brotli, rate-limit)
  ├── atm-web        :3000
  ├── atm-admin      :3001
  └── atm-backend    :4000
PostgreSQL 16   — контент
Redis           — кэш, сессии, throttler
MinIO (S3 API)  — медиа и документы
```

- Всё в `docker-compose.yml`, поднимается одной командой.
- Бэкапы: `pg_dump` ежедневно + снапшот бакета, хранение 30+ дней, отдельно от основного
  сервера, документированная процедура восстановления (п. XI).
- Хостинг в РК.
- Передача (п. XV): репозитории, дамп БД, `.env.example`, README с развёртыванием, доступы
  к хостингу/домену/сервисам, инструкция для редактора.

## 13. Риски

| Риск | Митигация |
|---|---|
| PageSpeed 90/80 при видеобаннере на главной | Постер как LCP, видео после load, на мобильных — статика. Замер с 4-го этапа |
| Заказчик меняет структуру разделов «на любом этапе» (п. IV) | Блочный контент + страницы как данные, а не как код |
| Контент от Заказчика приходит поздно | Наполнение — отдельный этап приёмки; запускаемся с реальной структурой и плейсхолдерами |
| Качество казахского и английского перевода | Статусы перевода в админке, публикация языковой версии только после подтверждения |
| 30 дней — жёсткий срок | Модульность позволяет вести бэк, админку и фронт параллельно с 12-го дня |
