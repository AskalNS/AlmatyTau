# Этап 1 (UX). Сценарии работы в административной панели

Требование п. V ТЗ: «CMS должна обеспечивать возможность самостоятельного управления контентом
сайта сотрудниками Заказчика **без привлечения Подрядчика**».

Это проверяемое требование: если редактор не может выполнить сценарий ниже без звонка
разработчику — CMS не сдана. Поэтому сценарии спроектированы до кода.

---

## 1. Структура админки

```
Контент  (доступно Редактору и Администратору)
  Главная страница      — состав и порядок секций
  Страницы              — блочные страницы, дерево
  Новости
  Медиагалерея          — альбомы и файлы
  Документы             — категории и файлы
  Вакансии
  Персоны               — Правление, Наблюдательный совет
  Ссылки                — госорганы, партнёры
  Меню                  — структура навигации
  Контакты и футер

Система  (только Администратор, п. V)
  Пользователи и роли
  Журнал действий
  Настройки
```

Редактор не видит системный блок вообще. Скрытие в интерфейсе — удобство; отказ в доступе
выдаёт бэкенд, даже если запрос отправлен напрямую в API.

---

## 2. Сценарий А — публикация новости (основной, ежедневный)

Самый частый сценарий. Целевое время — **под 3 минуты** без обучения.

| Шаг | Действие редактора | Поведение системы |
|---|---|---|
| 1 | Новости → «Создать» | Открывается карточка, активна вкладка языка `RU` |
| 2 | Вводит заголовок | Slug генерируется автоматически, доступен для правки |
| 3 | Загружает обложку | Автоматически: WebP/AVIF, 4 размера. **Требует заполнить `alt`** — без него не сохранить |
| 4 | Собирает тело из блоков | Блоки добавляются, перетаскиваются, удаляются |
| 5 | Переключает на `KK`, вводит перевод | Метаданные (дата, обложка) общие, тексты — отдельные |
| 6 | `EN` оставляет пустым | Вкладка помечена «не переведено» |
| 7 | «Предпросмотр» | Открывается реальная страница сайта в режиме черновика по секретной ссылке |
| 8 | «Опубликовать» | Публикуется **только RU и KK**. На английской версии новости нет |
| 9 | — | Инвалидация ISR-кэша, обновление sitemap, запись в журнал действий |

**Принципиальное решение:** при отсутствии перевода сущность не показывается на этом языке,
а не подменяется русским текстом. Это прямое следствие п. III ТЗ («независимое редактирование»),
и это же защищает Заказчика от смешанного контента на казахской версии госресурса.

## 3. Сценарий Б — редактирование раздела «О компании»

| Шаг | Действие | Поведение |
|---|---|---|
| 1 | Страницы → «О компании» | Список блоков страницы |
| 2 | Меняет текст в блоке `text` | Инлайн-редактирование |
| 3 | Добавляет блок `stats` с 3 показателями | Блок появляется в конце, перетаскивается на нужное место |
| 4 | Добавляет блок `video` | Ссылка на видео или загрузка файла |
| 5 | «Сохранить как черновик» → «Опубликовать» | Черновик и опубликованная версия хранятся раздельно |

Редактор **не может** сломать вёрстку: он оперирует блоками из готовой библиотеки, а не HTML.
Произвольный HTML не принимается — это одновременно и защита от XSS (п. X.III), и защита
от разрушения дизайна.

---

## 4. Сценарий В — Заказчик меняет структуру разделов

П. IV ТЗ: структура, наименования и порядок разделов могут меняться **на любом этапе**.
Это должно работать без релиза.

| Задача Заказчика | Как решается | Нужен разработчик? |
|---|---|---|
| Переименовать «Медиацентр» → «Пресс-центр» | Меню → правка названия по каждому языку | Нет |
| Поменять разделы местами | Перетаскивание в дереве меню | Нет |
| Добавить подраздел «Пресс-релизы» | Создать страницу → добавить пункт меню | Нет |
| Временно скрыть раздел | Переключатель видимости | Нет |
| Скрыть раздел только на английской версии | Видимость задаётся по каждому языку | Нет |
| Добавить блок нового типа («таймлайн») | Новый компонент + схема | **Да** |

Меню хранится в БД как дерево. Граница проведена честно: всё, что ТЗ разрешает менять
Заказчику, меняется из админки; новый *тип* блока — разработка.

## 5. Сценарий Г — загрузка документа (п. 4.1)

| Шаг | Действие | Поведение |
|---|---|---|
| 1 | Документы → «Загрузить» | Выбор файла |
| 2 | Система проверяет | MIME по содержимому, а не по расширению; whitelist форматов (п. X.III) |
| 3 | Указывает название по языкам, категорию, дату | Категории создаются редактором |
| 4 | Публикует | Документ попадает в каталог, индексируется поиском |
| 5 | Через месяц загружает новую редакцию | «Заменить файл» — **URL документа сохраняется**, старые ссылки не ломаются |

Версионность здесь не украшение: на внутренние НПА ссылаются из писем и других документов.
Загрузка новой редакции как отдельной записи оставила бы битые ссылки.

## 6. Сценарий Д — управление пользователями (только Администратор)

| Шаг | Действие | Поведение |
|---|---|---|
| 1 | Пользователи → «Пригласить» | Ввод e-mail и роли |
| 2 | Выбирает роль: Администратор / Редактор | Ровно две роли, как в п. V ТЗ |
| 3 | Сотрудник получает письмо | Ссылка одноразовая, ограничена по времени |
| 4 | Задаёт пароль | Парольная политика: длина, классы символов, проверка по списку утечек |
| 5 | Настраивает 2FA | **Обязательно для Администратора** (п. X.II), для Редактора — рекомендуется |
| 6 | Вход | Rate-limit; после N неудач учётная запись блокируется (Brute Force, п. X.II) |

## 7. Журнал действий (п. X.IV)

Доступен только Администратору. Фиксируется: кто, что, когда, из какого IP,
что было и что стало.

| Время | Пользователь | Действие | Объект |
|---|---|---|---|
| 21.07 14:32 | Ахметова А. (редактор) | Опубликовала | Новость «…» (RU, KK) |
| 21.07 14:05 | Ахметова А. (редактор) | Заменила файл | Документ «Положение о…» |
| 21.07 09:12 | Сериков Б. (админ) | Изменил роль | Пользователь → Редактор |
| 21.07 09:03 | — | **Неудачный вход ×5** | admin@… · 195.xx.xx.xx |

Фильтры по пользователю, типу действия и датам. Срок хранения — не менее срока гарантии.

## 8. Требования к юзабилити админки

Из п. V ТЗ следует, что админкой пользуются обычные сотрудники, а не ИТ-специалисты:

1. **Интерфейс на трёх языках** — редактор может не владеть русским. Язык интерфейса
   не связан с языком редактируемого контента.
2. **Автосохранение черновика** каждые 30 секунд + предупреждение при уходе со страницы.
3. **Предпросмотр — это реальная страница сайта**, а не приблизительный рендер в админке.
4. **Понятные ошибки на языке пользователя.** Не «422 Unprocessable Entity», а «Не заполнено
   описание изображения — оно обязательно для версии для слабовидящих».
5. **Никакого HTML и Markdown** в полях. Блоки и визуальный редактор.
6. **Медиабиблиотека с переиспользованием** — одно фото загружается один раз.
7. **Мобильная работоспособность** — публикация новости с телефона на выезде.

## 10. Открытые вопросы к Заказчику

1. **Сколько сотрудников** будет работать с админкой и в каких ролях? Двух ролей из ТЗ хватает,
   или нужен сценарий «редактор готовит → руководитель утверждает публикацию»?
2. **Нужна ли модерация публикации?** ТЗ её не требует, но для госресурса это частый запрос.
   Если нужна — добавляется статус «На согласовании» и роль согласующего.
3. **Кто отвечает за переводы** на казахский и английский? От этого зависит, нужен ли статус
   «отправлено на перевод» в карточке.
4. **Язык интерфейса админки** по умолчанию.
